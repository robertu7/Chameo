# Chameo UI, UX, performance, code, and documentation review

Reviewed version **0.5.6**, commit `1352ff1b033a01487a3a19761967904778bafa5a`. The audit began October 3 and continued October 4, 2026. This is a review of the current repository, rather than a branch diff. Application source and existing documentation were not changed.

The app has clear feature boundaries, substantial behavioral tests, and deliberate native macOS integration. The most consequential weaknesses are state ownership, asynchronous transaction boundaries, and release recovery. **Eleven actionable findings** follow: ten P2 findings and one P3 documentation finding. P2 means a concrete problem to address in the normal engineering queue; P3 means a lower-priority correction. Ordering reflects practical impact, not a claim that every scenario was observed live.

## Findings

### 1. P2 — A stale refresh can remove newly enabled reminders

**Evidence:** [ReminderService.swift:160](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Services/ReminderService.swift:160), lines 160–164, snapshots stored preferences before joining the serial notification queue. [ReminderSettingsView.swift:163](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Views/ReminderSettingsView.swift:163), lines 163–177, writes preferences only after scheduling returns.

**Trigger and impact:** Enable reminders while authorization/scheduling is suspended. An app activation or wake refresh reads the old disabled preference and queues cleanup behind scheduling. That cleanup removes the new requests even after Settings persists `enabled=true`. Changing an existing schedule can similarly reconcile the old schedule. Settings then disagrees with the operating system.

**Reproduction:** The isolated probe finished with `storedEnabled=true, pending=0` after removing 60 newly scheduled requests. See [reminder-race.txt](/Users/john/Documents/Projects/Chameo/docs/reviews/full-review-2026-10-03/reminder-race.txt). Its copied sources and fake boundaries are preserved in the adjacent `reminder-race/` directory. This reproduction did not touch real notifications.

**Fix:** Treat preference persistence and notification reconciliation as one serialized transaction. Resolve refresh state inside that transaction, with a revision or equivalent ordering guarantee so refresh cannot consume a pre-commit snapshot. Add enable/change/disable versus activation-refresh interleaving tests; moving just one read without coordinating the preference commit is insufficient.

### 2. P2 — Switching tabs silently discards an unsaved photo

**Evidence:** [CameraView.swift:27](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Views/CameraView.swift:27) owns the only captured draft in view-local `@State`. [ContentView.swift:26](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Views/ContentView.swift:26), lines 26–33, removes that view when Library is selected. Navigation remains available during capture and save.

**Trigger and impact:** Capture a photo, open Library before saving, then return to Camera. The draft has no retained owner or explicit discard confirmation. A capture finishing after navigation can also publish its result into detached view state. Popover and standalone hosts have separate draft state, so changing surfaces cannot restore the same draft.

**Fix:** Give capture/review state and the in-flight save a shared owner with an explicit draft lifecycle. Preserve the draft across navigation or ask before discarding it. Test capture → Library → Camera, surface handoff, and navigation during capture/save. This is a high-confidence code finding; hardware reproduction remains pending.

### 3. P2 — Location consent promises less precision than the app saves

**Evidence:** [English permission strings:3](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Resources/Localization/en.lproj/InfoPlist.strings:3), lines 3–4, describe city/country metadata. [LocationService.swift:17](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Services/LocationService.swift:17) requests hundred-meter accuracy; [PhotoLibraryService.swift:89](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Services/PhotoLibraryService.swift:89) stores the returned `CLLocation`, including coordinates. A city/country label in Library is a presentation choice, not coarsening of the saved location.

**Trigger and impact:** With Add Location enabled, photo metadata can contain substantially more precise coordinates than the permission explanation suggests. Sharing a photo with location metadata can expose those coordinates.

**Fix:** Disclose geographic coordinates and their sharing implications consistently in every localization, fallback bundle string, and privacy document, or intentionally coarsen the saved location to match the existing promise. Keep the choice visible beside the optional toggle. This was verified in source, not by collecting the user's location.

### 4. P2 — Calendar rendering repeatedly normalizes the whole photo history

**Evidence:** [CalendarLibraryView.swift:62](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Views/CalendarLibraryView.swift:62), lines 62–67, asks for a status for each grid date. [DailyCaptureStatus.swift:48](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Models/DailyCaptureStatus.swift:48) rebuilds a set of every capture's start-of-day on each call. `assetsByDay` also regroups/sorts the library as a computed view property.

**Measured cost:** Median time for the existing model's 42 status calculations, 15 optimized iterations, Gregorian calendar in Asia/Bangkok:

| Captures | Existing calculations | Lookup with precomputed day set |
| ---: | ---: | ---: |
| 365 | 15.4 ms | 0.093 ms |
| 1,000 | 41.4 ms | 0.092 ms |
| 3,650 | 148.3 ms | 0.093 ms |
| 10,000 | 406.6 ms | 0.093 ms |

These are model timings, not measured UI frame times. The cached comparison excludes one-time cache construction and measures the captured-day lookup path. At larger histories, even the existing model work alone exceeds Apple's responsiveness guidance. See [Apple's responsiveness guidance](https://developer.apple.com/documentation/xcode/improving-app-responsiveness).

**Fix:** Build a captured-day set, earliest tracked day, and grouped assets when the asset/calendar/time-zone snapshot changes. Make per-cell status lookup constant-time and invalidate the cache on relevant changes. The benchmark source and output are saved as [calendar-benchmark.swift](/Users/john/Documents/Projects/Chameo/docs/reviews/full-review-2026-10-03/calendar-benchmark.swift) and [calendar-benchmark.txt](/Users/john/Documents/Projects/Chameo/docs/reviews/full-review-2026-10-03/calendar-benchmark.txt).

### 5. P2 — Album creation can reenter despite its serialization claim

**Evidence:** [PhotoLibraryService.swift:196](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Services/PhotoLibraryService.swift:196), lines 196–207, checks for an existing album, then suspends inside `PHPhotoLibrary.performChanges`. The actor can admit another same-name caller during that suspension. [Architecture:83](/Users/john/Documents/Projects/Chameo/docs/architecture.md:83) explicitly claims overlapping saves/settings actions cannot create duplicates.

**Trigger and impact:** Two overlapping same-name find-or-create operations both observe no album before either transaction finishes. Each can create a separate album. Subsequent lookup chooses the first exact-name album, potentially hiding captures placed in the other one.

**Fix:** Coalesce an in-flight creation task per normalized name, or explicitly queue the complete check/create/refetch operation. Test with a controllable fake Photos boundary that admits a second request during the first suspension. Actual duplicate creation in PhotoKit was not performed during this audit.

### 6. P2 — Library thumbnail tasks do not cancel their Photos requests

**Evidence:** [PhotoLibraryService.swift:132](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Services/PhotoLibraryService.swift:132), lines 132–158, discards the image request ID and has no task-cancellation handler. [CalendarLibraryView.swift:586](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Views/CalendarLibraryView.swift:586), lines 586–590, checks cancellation only after the request completes.

**Trigger and impact:** Rapidly select cloud-backed dates or leave Library while a high-quality thumbnail request is downloading. The old SwiftUI task is cancelled, but unnecessary Photos network/decode work remains alive until completion. The magnitude of bandwidth and energy impact was not measured.

**Fix:** Retain `PHImageRequestID`, cancel it through a race-safe `withTaskCancellationHandler`, and resume the continuation exactly once. Reuse the approach already present in Timelapse request state. Apple documents request-ID-based cancellation in [cancelImageRequest](https://developer.apple.com/documentation/photos/phimagemanager/cancelimagerequest(_:)?language=objc). Add cancellation-before-ID-assignment and late-callback tests.

### 7. P2 — Release recovery fails if publication already succeeded

**Evidence:** [release.yml:165](/Users/john/Documents/Projects/Chameo/.github/workflows/release.yml:165), lines 165–172, unconditionally creates the GitHub release. URL validation and feed publication occur afterward. The local release procedure promises recovery using the same immutable tag at [release skill:64](/Users/john/Documents/Projects/Chameo/skills/release-chameo/SKILL.md:64).

**Trigger and impact:** Release creation succeeds, then URL verification or the release job fails before the feed is published. Rerunning the complete workflow/manual recovery attempts to create an already existing release and stops before deployment. A deploy-only job failure can sometimes be retried independently, but the documented full recovery path remains broken.

**Fix:** Detect and verify an existing release and its immutable assets before reusing them. Resume missing publication steps without clobbering downloads; use the feed metadata/signatures corresponding to the actual published assets. Add a failure-after-creation recovery fixture. No external release was created to reproduce this workflow issue.

### 8. P2 — Concurrent releases can replace the appcast with a stale snapshot

**Evidence:** [release.yml:19](/Users/john/Documents/Projects/Chameo/.github/workflows/release.yml:19), lines 19–21, scopes the workflow lock per tag. Existing feed fetch/merge/signing happens at lines 105–134; the shared feed lock is acquired only in the deployment job at [line 192](/Users/john/Documents/Projects/Chameo/.github/workflows/release.yml:192).

**Trigger and impact:** Different tags build against the same old appcast. Serialized deployments still write their independently generated snapshots, so the later deployment can omit the version published by the earlier one. A cryptographically valid feed can therefore lose the newest update; the final signature check cannot detect this semantic regression.

**Fix:** Serialize fetch → merge → sign → publish as one shared transaction, including feed repair, or use a compare-and-swap approach and regenerate when the published snapshot changed. Verify retained/current build numbers after publication. Test overlapping tag runs and old-tag recovery. This is a verified workflow interleaving, not an observed production incident.

### 9. P2 — Bundle validation accepts ineffective entitlements

**Evidence:** [verify_app_bundle.sh:101](/Users/john/Documents/Projects/Chameo/script/verify_app_bundle.sh:101), lines 101–108, checks that selected keys can be printed, not their values. `PlistBuddy Print` returns success for a Boolean `false`. Location, user-selected read/write, and app-scope bookmarks are not checked at all.

**Trigger and impact:** A mistakenly disabled sandbox or camera entitlement still passes this gate if its key exists. Missing feature grants can likewise pass while location, export access, or reopened results fail in the signed app. The current checked-in entitlements are enabled; this is a validation gap, not evidence that the current bundle is unsandboxed.

**Fix:** Assert required Boolean values and expected Sparkle Mach-service names, and validate all required grants. Add negative fixtures for false/missing/malformed entitlements. Keep signature verification separate from entitlement semantics.

### 10. P2 — Pending login registration cannot be cancelled through the app

**Evidence:** [LaunchAtLoginService.swift:9](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Services/LaunchAtLoginService.swift:9), lines 9–16, unregisters only `.enabled` and treats `.requiresApproval` as needing registration again. [GeneralSettingsView.swift:98](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Views/GeneralSettingsView.swift:98) resets the switch from `isEnabled`, so pending registration appears off.

**Trigger and impact:** Register Chameo for login when macOS requires user approval, or revoke an existing approval. The service remains registered, but the off switch cannot unregister it. Pending status and approval guidance are not reliably retained across reopening. Apple's installed SDK header explicitly defines `.requiresApproval` as successfully registered but awaiting consent.

**Fix:** Model registered, pending approval, and enabled separately. Unregister both enabled and pending services, skip redundant registration, and display persistent approval status with a System Settings action. Add policy tests for all `SMAppService.Status` values. The test app intentionally disables this feature; no real login registration was changed.

### 11. P3 — Permission and distribution documentation contradict current behavior

**Evidence:** [permissions.md:80](/Users/john/Documents/Projects/Chameo/docs/permissions.md:80), lines 80–81, says both that export requests notifications and that it never does. [README.md:160](/Users/john/Documents/Projects/Chameo/README.md:160) retains the obsolete request claim. The current export controller and UI checklist agree that notifications are used only for reminders.

Other consequential corrections: [production-readiness.md:41](/Users/john/Documents/Projects/Chameo/docs/production-readiness.md:41) omits broad Pictures-folder write access from its permission summary; [development.md:125](/Users/john/Documents/Projects/Chameo/docs/development.md:125) describes all tagged releases as prereleases although the workflow selects stable/prerelease status from the version. Some historical review image links point to temporary or outdated paths.

**Fix:** Correct the current README/privacy/developer contract together. Clearly label historical evidence and use durable links for retained screenshots. Update the album-serialization claim after finding 5 is fixed. This audit report does not itself amend those documents.

## Code quality and best practices

Established strengths include narrow AppKit window ownership, typed preference/domain models, an explicit camera lifecycle, throttled on-device Vision work, staged video replacement, cancellation-aware export request state, local-copy integrity checks, inline destructive confirmation, and testable service boundaries. The pinned Sparkle dependency and action commits, explicit workflow permissions, and signed-feed validation are useful distribution safeguards. Documentation honestly states the ad-hoc signing/notarization and manual-validation limits.

The important structural improvement is to own asynchronous transactions in services/stores rather than splitting them between view state, persisted preferences, and queue operations. A serial queue or actor does not automatically make a multi-step operation atomic across suspension. Findings 1, 2, and 5 are examples; solving them at their shared owners is more useful than broad cosmetic refactoring. No repository-wide formatting or rename exercise is warranted by this review.

One additional performance opportunity needs profiling before prioritization: [TimelapsePhotoLoader.swift:156](/Users/john/Documents/Projects/Chameo/Sources/Chameo/Services/TimelapsePhotoLoader.swift:156) materializes the full local original before export scales it to 1080 × 1080. A hypothetical 6000 × 4000 four-byte raster is about 96 MB before other buffers. Consider orientation-correct ImageIO downsampling to the required aspect-fill dimensions while retaining original bytes on disk. This is an allocation estimate, not measured resident memory or a demonstrated crash; it is excluded from the eleven findings.

## Recommended work order

1. Repair reminder scheduling/persistence and retain the capture draft; add the targeted interleaving/lifecycle regressions.
2. Correct location consent and coalesce same-name album creation.
3. Make feed publication transactional and release recovery resumable; strengthen entitlement validation.
4. Cache calendar history and cancel obsolete thumbnail requests.
5. Handle pending login approval and reconcile the current documentation.
6. Complete the live hardware and accessibility pass when the Mac is unlocked, then profile export peak memory and camera CPU/energy with realistic inputs.

Existing tests are a strong foundation, but they do not yet cover the reproduced stale-preference race, view-draft lifecycle, reentrant album creation, release publication interleavings, or invalid signed entitlement values. Those focused regression scenarios should accompany the corresponding fixes.
